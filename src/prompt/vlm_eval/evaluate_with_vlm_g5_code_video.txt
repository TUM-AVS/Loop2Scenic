** THREE-STAGE EVALUATION PROCEDURE **
1. Generate an **Observed DSL** using the provided Scenic code AND BEV video.

The Observed DSL MUST be generated from the Generated Scenario evidence only (code + video). Do NOT use the Target DSL, the Original User Input, or any other specification while generating the Observed DSL. Do NOT invent events that appear in neither the code nor the video. The Observed DSL must not be modified during Stage 2 or Stage 3.

How to build the Observed DSL from code + BEV video:

Identify Ego and Adversarials (STRICT):
- The camera continuously tracks and moves with the ego vehicle.
- The ego vehicle is ALWAYS near the center of the screen throughout the video.
- There is exactly ONE ego. Its `object` MUST be one of: Car, Motorcycle, Truck.
- Do not override ego identity with Target DSL or user input.
- Every other vehicle, pedestrian, cyclist, or similar dynamic actor is an adversarial. Record each one separately.
- Each adversarial `object` MUST be one of: Car, NPCCar, Bicycle, Motorcycle, Truck, Pedestrian, Gnome.
- Stationary actors still count (e.g., parked Car, standing Pedestrian).

Describe Spatial Relation:
- Name the road geometry (straight road, intersection, highway, etc.).
- Place the ego and every adversarial using relative terms (in front of / behind / on the left of / on the right of the ego, or relative to road geometry such as left/right arm of an intersection). Do NOT use north / south / east / west.
- Record initial spawn layout and how relative positions evolve when visible.

Describe Ego Behavior:
- Focus on relative driving actions (e.g., turn left/right relative to the ego's own orientation), not absolute screen directions (top-to-bottom vs left-to-right on the map).
- Note visible speed changes (too fast / too slow / braking / accelerating) when clear.
- Do NOT put spatial placement inside `ego.behavior`. Spatial facts belong ONLY in `spatial_relation`.
- Map what you see onto Scenic-style maneuvers when evidence supports them (use natural language, not code names):
  - FollowLaneBehavior: stays centered in the current lane and continues along it (drives straight in-lane; may go straight through an intersection by default).
  - LaneChangeBehavior: clear lateral move into an adjacent lane until aligned with that lane's centerline (left or right). Aborted lane change = starts the lateral move, then returns to the original lane.
  - FollowTrajectoryBehavior: follows a multi-segment path (e.g., approach → connecting lane → exit lane), often through an intersection along a planned route.
  - TurnBehavior: turns inside an intersection (left/right) along a turning path; slower than straight travel.
  - DriveAvoidingCollisions: follows the lane but suddenly brakes hard when another actor is too close ahead.
  - ConstantThrottleBehavior / AccelerateForwardBehavior: keeps pushing forward with little steering correction (may look like steady forward creep).
  - Brake / stop / remain stationary: visible deceleration to a halt, or no movement across frames.
  - Reverse: moves backward relative to its heading.
- Lane-change check (CRITICAL): compare ego vs lane markings across early / mid / late frames. Crossing into another lane = lane change; staying parallel in one lane = FollowLane, NOT lane change.

Describe Adversarial Behaviors:
- Write an independent behavior for each adversarial (same relative-maneuver priority and Scenic-style vocabulary as ego).
- Do not omit a visible adversarial because it seems irrelevant.
- Do NOT put spatial placement inside any adversarial `behavior`. Spatial facts belong ONLY in `spatial_relation`.
- Pedestrian-specific Scenic-style maneuvers when supported by evidence:
  - WalkForwardBehavior / WalkBehavior: walks roughly along its current heading at walking speed.
  - CrossingBehavior: crosses the roadway (often near-perpendicular), possibly timed with a vehicle approach.
  - Remain stationary: standing still on road or sidewalk.

Describe Requirements & Restrictions (only what is visible):
- Traffic-light state / compliance if visible.
- Starting layout relative to road topology (e.g., distance to an intersection) when visible.
- How the video ends (premature cutoff, collision, completed maneuver, etc.).

Describe Road Side Structures:
- Only list objects from the Allowed Structure Vocabulary. Ignore everything else.
- For each, record object type and position relative to ego / road geometry.

Describe Temporary Modifications:
- Only list objects from the Allowed Modification Vocabulary that are on or affecting the drivable roadway.
- For each, record object type and exact placement (e.g., center of lane, blocking crosswalk).

2. Compare the Observed DSL with the Target DSL and Evaluate whether they semantically match.

The Target DSL is the ground-truth specification. Evaluate each of the seven fields independently.
Use ONLY Observed DSL + Target DSL in this stage. Do NOT re-watch the video to invent new facts; do NOT modify Observed DSL.
Both Observed DSL and Target DSL use the same 7 JSON fields.

For scalar fields (`scenario`, `ego`, `spatial_relation`, `requirements_and_restrictions`), output a single boolean each: TRUE if the Observed value semantically matches the Target value; otherwise FALSE.

Example for spatial_relation:
- Target: ego and adversarial start in the same lane; Observed: they start in different lanes → FALSE
- Target: adversarial is a lead vehicle; Observed: adversarial is in front of the ego → TRUE

For list fields (`adversarials`, `road_side_structures`, `temporary_modifications`), evaluate one Target item at a time:

- If the Target list length is 0, output `[]` for that field.
- Walk through the Target list in order. For each Target item, search the Observed list for an unused match.
- One-to-one matching: each Observed item may match at most one Target item. Once matched, it cannot be reused.
- What counts as a match:
   - adversarials: same object type AND semantically equivalent behavior
   - road_side_structures / temporary_modifications: same object type AND same position
- If no unused Observed item matches, mark that Target item FALSE (including when the Observed list is shorter than the Target list).
- Output a boolean list with the same length as the Target list. Extra Observed items that were never matched are ignored.
- Example:
    Target adversarials: 8
    Observed adversarials: 5
    Matches: 3
    Output: [true, true, true, false, false, false, false, false]

Premature cutoff (CRITICAL):
If the Target requires an event, behavior, or outcome that never becomes visible before the video ends, mark the corresponding scalar field or list item FALSE. Do not assume the missing event happened off-camera or after the clip.

3. Scoring from the evaluation result in step 2.

Convert the seven evaluation fields into seven KPI booleans (`kpi_matches`), then count how many are TRUE to get the score.

Scalar KPIs — copy the evaluation boolean as-is:
1. scenario
2. ego
3. spatial_relation
4. requirements_and_restrictions

List KPIs — TRUE only if the evaluation list is empty (`[]`) OR every entry is TRUE; otherwise FALSE:
5. adversarials
6. road_side_structures
7. temporary_modifications

Empty Target lists intentionally pass their list KPI (evaluation `[]` → KPI TRUE).
Do not average list entries (e.g. [true, true, false] is FALSE, not a partial credit).

`kpi_passed` = number of TRUE values in `kpi_matches`.
`score` = map from `kpi_passed`:
7 → 100 | 6 → 90 | 5 → 80 | 4 → 70 | 3 → 50 | 2 → 20 | 1 → 10 | 0 → 0

Only these seven KPI booleans affect the score.
